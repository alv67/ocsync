# Feasibility spike — 2026-10-26

Environment:

- OpenCode `2.0.29`
- Bun `1.4.4`
- Ubuntu 26.04
- Git `2.53.0`

The spike validated the assumptions behind the architecture. It used isolated OpenCode servers with temporary databases and temporary project directories.

## Results

### Session export and import work through the official API

`GET /api/experimental/session/{id}/export` returns `{ info, messages }`. `POST /api/experimental/session/import` accepts the same object plus a target `location`.

Observed behavior:

- importing a session ID that already exists returns `409 Conflict`;
- the CLI `opencode session import` prints `Session already exists` but exits with code `0`, so the engine uses the HTTP API for reliable conflict detection;
- deleting the local session and importing again succeeds;
- the imported session keeps its ID and messages;
- `info.time.created` is preserved, while `info.time.updated` is set to the import time;
- `info.location.directory` is replaced with the target directory.

Conclusion: replacement is possible, but only through delete + re-import, and the revision model must not compare `time.updated` across machines.

### The active-session endpoint works

`GET /api/session/active` returns `{}` when no turn is running. The engine uses it to avoid touching sessions that are currently executing.

Open question: this endpoint does not report sessions that are merely open in a TUI or browser. Pulling an open-but-idle session needs an end-to-end UI test.

### Server plugins are a first-class extension point

A local plugin placed in `.opencode/plugins/<name>/index.ts` was discovered and loaded by OpenCode `2.0.29`. The loader also accepts the singular `.opencode/plugin` directory.

Verified in the running server:

- `setup(ctx)` ran;
- `Bun.spawn` worked and returned an exit code;
- `ctx.event.subscribe()` delivered live events;
- the cleanup function ran on plugin reload;
- the event stream includes events for every location on the server, so a plugin must filter by `event.location.directory`.

Relevant event types observed or defined by the V2 schema:

- `session.created`, `session.deleted`, `session.renamed`, `session.moved`, `session.archived`, `session.unarchived`
- `session.execution.started`, `session.execution.succeeded`, `session.execution.failed`, `session.execution.interrupted`
- `session.status` with `status.type` of `idle`, `busy`, or `retry`
- `session.idle` (deprecated, but still emitted)

The plugin context exposes `ctx.session.get`, `ctx.session.context`, and `ctx.session.remove`, but not `session.export` or `session.import`. The chosen integration is a thin plugin that spawns the `ocsync` CLI.

### Local service discovery works

The local OpenCode service registers itself at:

```text
~/.local/state/opencode/service.json
```

The file contains `url`, `password`, `pid`, and `version`. HTTP Basic authentication with username `opencode` (or `OPENCODE_SERVER_USERNAME`) and the registered password works against `/api/info`. `ocsync` uses this path for local operation and accepts `--server` plus `--password` for remote servers.

## Go/no-go

**Go.**

The official API supports the required transfer operations. The server plugin is a supported extension point and can spawn the CLI. No patch, fork, or database write is required.

The remaining risks are product risks, not platform blockers:

1. Pulling a session that is open but idle in a client.
2. Loading a server plugin in the Windows desktop app (expected, not yet tested).
3. Child sessions: the current MVP skips them to avoid deleting them when a parent is replaced.
4. Remote deletion handling.
5. Snapshot and revert state do not travel with a transcript.

These are tracked as separate work items in the GitHub Project.
